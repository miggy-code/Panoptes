# Proxy hooks

> **Status: draft, not frozen.** Written before the implementation so the
> contract can be reviewed. Panoptes does not promise this API until it is
> approved and this line is removed. Decided so far: `after_exchange` is owed
> for every entered exchange; every exchange has a `correlation_id`; one hooks
> object per proxy.

The Panoptes reverse proxy observes model-API traffic: it forwards each request
unchanged, parses it and the response, prices the usage and records events. It
never decides anything and never blocks. Anything that decides plugs in through
two hooks, one before the request leaves and one after the exchange ends.

```python
from panoptes.hooks import Exchange, ProxyHooks, Reject
from panoptes.proxy import Upstream, start_proxy

class MyHooks(ProxyHooks):
    def before_forward(self, exchange: Exchange) -> Reject | None: ...
    def after_exchange(self, exchange: Exchange) -> None: ...

server = start_proxy(
    db=my_audit_db,                     # or db_path="~/.panoptes/audit.db"
    upstreams={"openai": Upstream("https://api.deepseek.com", name="deepseek")},
    pricing=my_pricing_table,
    hooks=MyHooks(),
)
```

`panoptes.hooks` imports no HTTP client, so it loads without the `[proxy]`
extra. With `hooks=None` (the default) the proxy is pure observe and
pass-through: no hook code runs, nothing new is buffered, and behaviour is
unchanged.

## What a hook may and may not do

A hook may **reject** the request, **set the identity** the exchange is recorded
under, **set or remove outbound headers** (that is how a credential is
injected), and keep **private state** from `before_forward` to
`after_exchange`. It cannot change the request body, the target or the
response. Panoptes forwards exactly the bytes it received, and what it records
is what it observed, not what a hook wished.

Panoptes never learns *why* a hook rejects, and never interprets the reason.

## Lifecycle

```
client request
  └ parse target, read body, parse JSON, build the request events
      └ before_forward(exchange)            ← entered: after_exchange is now owed
          ├ Reject → record, answer the client, never forward
          ├ raises → 502, record, never forward
          └ None   → record the request, forward
              └ response relayed to the client, response events recorded
                  └ after_exchange(exchange)   ← exactly once
```

**Invariant: if `before_forward` was entered, `after_exchange` is called
exactly once**, whatever happens: a rejection, a hook exception, an upstream
error, a client that disconnects mid-stream, or an unexpected exception in the
proxy itself. A hook that reserved something in `before_forward` can therefore
always settle or release it in `after_exchange`; `exchange.outcome`,
`request_sent` and `complete` say what happened. `after_exchange` runs after
the response has been sent, so it cannot change it, and a slow hook does not
delay the client.

### Requests Panoptes refuses before the hook

A request that is malformed (not a strict JSON object, ambiguous framing,
duplicate keys), oversized, or unroutable (no supported provider route) is
answered with an error by Panoptes **before** `before_forward` is entered. The
hook never sees it and no `after_exchange` follows. Panoptes records the refusal
as an observation where it can, but a hook that keeps its own decision log will
have no entry for these requests. That is fail-closed: nothing was forwarded.
If your audit of model requests must account for every request, join your log
against Panoptes' events on `correlation_id` rather than assuming one entry per
request.

## `Exchange`

One object per proxied request, passed to both hooks. Request fields are
read-only; a hook mutates only `identity`, `outbound_headers` and `state`.

### Request fields

| Field | Meaning |
|---|---|
| `exchange_id` | unique id of this request, generated by Panoptes |
| `correlation_id` | the id every event of this exchange carries: the client's `X-Panoptes-Correlation-Id` if it sent a valid one, else `exchange_id` |
| `correlation_source` | `"client"` (asserted, never trusted) or `"proxy"` |
| `provider` | the **wire protocol** the request speaks: `"openai"`, `"anthropic"`, `"gemini"` or `"unknown"` |
| `upstream_name` | the configured upstream's name (see [Upstreams](#upstreams)); defaults to `provider`. With `Upstream("https://api.deepseek.com", name="deepseek")`, `provider` is `"openai"` and `upstream_name` is `"deepseek"` |
| `upstream_url` | the upstream origin, `scheme://host[:port]`, with no path, query or credentials |
| `method`, `path` | the request line as routed. Credential query parameters are removed (below) |
| `request_headers` | read-only header list as received, credentials included. Keeps repeated lines: `get_all(name)` returns every value in order, `get(name)` the first, `items()` every `(name, value)` pair in received order and case. Lookup is case-insensitive |
| `query_credentials` | tuple of the decoded values of every `key` query parameter that was removed from the URL, in order (Gemini sends its credential this way) |
| `request_body` | the raw body bytes, as received |
| `request_json` | the body parsed as a strict JSON object, or `None` |
| `request_events` | the parsed request events (`model_request` and any `tool_result`) as deep copies; mutating them changes nothing |

`request_headers` and `query_credentials` are how a hook sees **every**
credential the client presented, including two different ones in one request
(for example a bearer token and a different `x-api-key`, or a header plus
`?key=`). Neither appears in `repr(exchange)` or in any recorded event, and the
recorded `path` never contains a credential query value.

When hooks are installed, credential query parameters are always removed from
the URL Panoptes forwards, even if the hook injects nothing. This keeps a
client's credential from travelling upstream beside an injected one. A hook
that wants the client's own credential to reach the provider copies it into
`outbound_headers` (for Gemini, `x-goog-api-key`) from `query_credentials`.
Without hooks nothing is stripped and the query is forwarded as received.

### Fields a hook may set

| Field | Meaning |
|---|---|
| `identity` | the identity this exchange is recorded under; see below |
| `outbound_headers` | case-insensitive map of the headers that will be sent upstream |
| `state` | a dict private to the hook, carried to `after_exchange` |

#### `identity`

```python
exchange.identity.agent_type      # str
exchange.identity.session_id      # str
exchange.identity.run_id          # str | None
exchange.identity.parent_run_id   # str | None
exchange.identity.user            # dict | None, e.g. {"id": "alice", "auth_method": "run-token"}
```

Panoptes seeds it as it does today: from the client's `X-Panoptes-Agent` and
`X-Panoptes-Session` headers, the User-Agent, and a generated `run_id`. Those
are **client assertions**, nothing more. A hook that authenticates the caller
(for example by resolving a token to a run) overwrites the fields it knows, and
the exchange is joined to that run, not to whatever the client claimed. Set
every field you rely on; a field you leave alone keeps its seeded value.

Panoptes reads `identity` once, when `before_forward` returns, and records every
event of the exchange, request and response alike, under it. That includes the
events of a rejected exchange and of a `hook_error` (the identity the hook set
before it raised is used when it is valid; otherwise the seeded identity is).
Changes after `before_forward` returns, including in `after_exchange`, are
ignored: `exchange.identity` then holds what was recorded.

Values are validated as identifiers (at most 256 characters, no control
characters, no secret-shaped text). An invalid value is a hook error (below).

#### `outbound_headers`

Starts as the request's headers as Panoptes would forward them today: repeated
lines combined, hop-by-hop headers (including any header the client's
`Connection` header nominates), `host` and `X-Panoptes-*` headers removed. It
**still contains the client's credentials**; a hook that injects a provider key
removes them first (`panoptes.hooks.CLIENT_CREDENTIAL_HEADERS` lists
`authorization`, `x-api-key` and `x-goog-api-key`).

Lookup is case-insensitive (`h["Authorization"]` and `h["authorization"]` are
one entry). Values must be strings without CR, LF or NUL. Nothing in
`outbound_headers` is ever recorded.

After the hook returns, Panoptes re-applies only its own fixed invariants:
the static hop-by-hop names (`connection`, `keep-alive`, `proxy-authenticate`,
`proxy-authorization`, `proxy-connection`, `te`, `trailer`, `trailers`,
`transfer-encoding`, `upgrade`) and `host` are dropped, and
`Accept-Encoding: identity` is forced so responses stay inspectable. **It never
removes a header the hook set because of anything in the client's request.**
In particular, headers nominated by the client's `Connection` header are removed
from the client's set *before* the hook runs, so a request carrying
`Connection: x-api-key` loses the client's `x-api-key` and cannot make Panoptes
strip an `x-api-key` the hook injects.

### Fields set for `after_exchange`

| Field | Meaning |
|---|---|
| `outcome` | one of the values below |
| `request_sent` | see below |
| `status` | the HTTP status the client received, or `None` if none was sent |
| `complete` | `True` if the response was relayed and captured in full; `False` if the relay broke (client disconnect, upstream drop) or the audit capture was truncated, so usage may be missing or partial; `None` if no response was produced |
| `response_events` | the response events recorded (`model_response`, `tool_call`) as deep copies; empty if none |
| `usage` | token counts from the `model_response` event's `cost` (`tokens_in`, `tokens_out`, and cache/reasoning counts where the provider reports them), or `{}` |
| `estimated_usd_micros` | the exact priced cost of the response in whole micro-dollars (an `int`), or `None` if unpriced: no rate table, an unknown model, or missing token counts. Panoptes never guesses a rate. Rounding is described in [api.md](api.md#pricing) |
| `estimated_usd` | the same figure as the float `cost.estimated_usd`, or `None`. Prefer the integer |
| `provider_error` | `True` if the upstream answered with a 4xx or 5xx |
| `duration_ms` | proxy-measured wall time for the exchange |

`repr(exchange)` omits headers, bodies and query credentials, so logging an
exchange cannot leak a credential.

#### `request_sent`

`False` means Panoptes can show the request never reached the provider.
`True` means it may have: a provider that received a request may have
generated, and billed, tokens even if no usable reply came back.

`request_sent` becomes `True` the moment Panoptes hands the request to the
upstream connection after it was established, and stays `True` whatever
follows: a read timeout, a truncated or broken stream, a client that
disconnects mid-stream, an upstream 5xx. It is `False` for a rejection, a hook
error, a `not_forwarded` exchange, and an upstream connection that failed to
establish (DNS, connect error or timeout, TLS handshake failure, pool
exhaustion).

This is deliberately conservative rather than exact to the byte: the HTTP client
does not report when the first byte is written, so Panoptes errs toward `True`.
That is the safe direction for a caller that settles money: it will never
release a reservation for a request the provider might have processed. A caller
may release only when `request_sent` is `False`, or when it is `True` and the
upstream answered with a 4xx/5xx (`provider_error`, which providers do not
bill).

#### `outcome`

| Value | Meaning |
|---|---|
| `"forwarded"` | the upstream answered (any status) and the response was relayed |
| `"upstream_error"` | no usable upstream response: connect error, timeout, unsafe framing, or oversized body. Panoptes answered 502/504. See `request_sent` for whether the provider may have received it |
| `"rejected"` | `before_forward` returned `Reject` |
| `"hook_error"` | `before_forward` raised or returned something invalid |
| `"not_forwarded"` | `before_forward` accepted, but Panoptes then refused to forward for its own reasons (for example the durable record of the request could not be written) |
| `"aborted"` | the exchange ended abnormally with no result, such as an unexpected proxy error |

## `before_forward(exchange) -> Reject | None`

Runs in the request thread, after the request events are built and before
anything is recorded or sent upstream. It sees the parsed request, the
provider and the raw bytes.

- **`None`**: forward. Panoptes records the request events under
  `exchange.identity`, applies `outbound_headers` and forwards.
- **`Reject(status, body, reason)`**: do not forward.
  - `status`: an integer 400-599 sent to the client.
  - `body`: a JSON-serializable object sent as `application/json`
    (default `{"error": reason}`). Panoptes adds nothing to it.
  - `reason`: a short code (a Panoptes identifier: at most 256 characters, no
    control characters or secret-shaped text). Recorded, never interpreted.

  Panoptes marks the request events `blocked`, records
  `attributes.hook = {"action": "reject", "status": ..., "reason": ...}` on
  them, writes them under `exchange.identity`, and answers the client. If that
  record cannot be written the request is still rejected and never forwarded.
- **An exception, or an invalid return value** (not `None`/`Reject`, a status
  outside 400-599, a body that is not JSON, a bad reason, an invalid identity
  or header value): Panoptes answers **502** with a generic body that does not
  include the exception text, records the request events as `blocked` with
  `attributes.hook.action = "error"`, logs the exception, and never forwards. A
  failing hook can never mean "forward anyway".

## `after_exchange(exchange) -> None`

Called exactly once per entered exchange, in the request thread, after the
response has been delivered (or the exchange has failed). All the `Exchange`
fields above are set. It is for settling: charge the priced cost, release a
reservation, emit your own record.

It cannot affect the exchange. An exception is logged and discarded; the next
request is unaffected. Make it idempotent.

## Upstreams

Panoptes routes a request to an upstream by its wire protocol, so a proxy
serves **one upstream per wire protocol**. By default that is the provider's
public API (or the `PANOPTES_*_UPSTREAM` environment variable, as today).
`upstreams` sets it explicitly and names it:

```python
upstreams={
    "openai": Upstream("https://api.deepseek.com", name="deepseek"),
    "anthropic": "https://api.anthropic.com",     # shorthand: name defaults to "anthropic"
}
```

Keys are wire-protocol names. `Exchange.provider` is always the wire protocol;
`upstream_name` is the operator's label and `upstream_url` the origin. Panoptes
attaches no meaning to the name. A hook maps `(provider, upstream_name)` to
whatever it calls the provider.

## Sharing the audit file and its chain

`start_proxy(db=<AuditDB>)` makes the proxy write through an `AuditDB` the
caller owns, so a hook's own sink and the proxy share one object. The proxy
neither migrates nor closes it. `db=` and `db_path=` are mutually exclusive;
`chain=` applies only when the proxy opens `db_path` itself.

Two `AuditDB` handles on one file also stay on **one chain**, so `db=` is a
convenience rather than a requirement. The chain tip is never cached on the
`AuditDB` object: every insert reads it from the database inside a
`BEGIN IMMEDIATE` transaction, so concurrent writers, from one process or
several, serialize on the file and extend the same chain.
`test_concurrent_batches_across_db_instances_do_not_fork_chain` exercises this.
A hook's decision events and the proxy's exchange events can therefore live in
one file under one chain and be joined on `run_id` and `correlation_id`.

## Concurrency and cost

Hooks run in the proxy's request threads and are called concurrently. They must
be thread-safe. Panoptes does not time-box a hook: a hook that blocks holds one
request thread (the proxy bounds concurrent requests), so keep hooks fast and
do not call back into the model API through the same proxy.

With no hooks the proxy does no extra work. With hooks, the cost is the
`Exchange` construction (deep copies of the request events) per request.

## Recorded events

A hook decides; Panoptes records what it observed. Request events carry
`correlation_id` and, when a hook acted, `attributes.hook`. They never carry
header values or query credentials. If your hook also writes its own records (a
decision log), join them to Panoptes' events on `run_id` and `correlation_id`.

## Not in this contract

- **Response-side hooks.** Inspecting or withholding a response (for example to
  block a tool call in a streamed answer) needs buffering and is a separate,
  opt-in hook that does not exist yet. This contract is request-side only.
- **Multiple hooks.** One `ProxyHooks` object per proxy. Compose several in your
  own class.
- **Per-request timeouts** for hooks.
- **Several upstreams for one wire protocol** in a single proxy.
